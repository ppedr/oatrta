# AGENTS.md quality guide and rubric

Shared reference for the `agents-md-audit`, `agents-md-refactor` and `agents-md-create` skills.

Source of the practices: "Writing an effective AGENTS.md", Agentic AI Foundation,
https://aaif.io/blog/writing-an-effective-agents-md. This file restates those practices as
testable criteria. When this file and the source disagree, the source wins; fix this file.

## 1. The one test

For every instruction ask: **would an agent act differently because it read this?**

- If the agent would do the same thing anyway (it can read the manifest, the tree, the code),
  the line is noise. Cut it.
- If the line removes a decision the agent would otherwise guess at, it is signal. Keep it and
  make it exact.

AGENTS.md is plain Markdown. There are no mandatory sections and no schema. A 15-line file can be
excellent. Never reward length, never punish a missing section when the repository has nothing
non-obvious to say there.

## 2. What belongs in the file

| Category | Good shape | Bad shape |
|---|---|---|
| Layout | Only what names do not reveal: which package owns a feature, which code is shared, where the real entry point is | A tree listing, a tour of every folder |
| Commands | Exact command plus where to run it: "From `services/api`, run `make test-unit`" | "Run the tests" |
| Tooling choices | The non-obvious choice and why: "Use `make build`, not `go build`; the target injects required flags" | Restating the default tool of the language |
| Boundaries | Generated paths and the source to edit instead; dependency direction between layers; public API and compatibility rules; actions that need human approval | "Be careful with the architecture" |
| Definition of done | What to run while iterating, what to run before finishing, how validation scales with the size of the change | "Make sure everything passes" |
| Conventions | Project-specific, concrete, with the canonical file to copy: "New handlers follow `internal/http/orders_handler.go`" | "Follow existing patterns" |

Specificity rule: a vague rule names nothing. Replace it with a file, a path, a command or a
dependency direction, or delete it.

## 3. What does not belong

- Facts visible in manifests or the source tree (language, framework, where tests live).
- Generic engineering advice ("write clean code", "follow best practices", "add tests").
- Directory listings copied from the repository.
- Broad repository overviews. They do not help an agent find the relevant code faster.
- Large copies of existing docs. Link to the doc; two copies drift apart.
- Credentials, secrets, private operational details.
- Template headings with no real content under them.

## 4. Enforcement belongs in tooling

- Style rules go in the formatter config. Layering rules go in static analysis.
- AGENTS.md points at those systems ("lint enforces import order; run `make lint`"). It is not
  the only safeguard.
- Instructions never replace access control or CI checks.

## 5. Topology: root and nested files

- A small repository usually needs one root file.
- A larger repository can add files next to the code they describe (per service, per app).
- Root holds repository-wide rules. Nested files hold area rules: language version, test
  commands, migration rules.
- On conflict, the file closest to the edited file wins. Explicit user instructions beat both.
- Nest only at real boundaries: different language, build system, validation process,
  architecture or ownership.
- Agents differ in how they discover and merge nested files. Test with the agents actually used.

## 6. Evidence caveats (why these skills are conservative)

- Research on context files is mixed. Short, specific files have reduced runtime and tokens.
  Other results show no gain in task success and more steps and cost.
- Files written by developers did better than files generated by an LLM. Generated files only
  helped when other documentation was absent.
- Consequences for these skills: never fill a file with discoverable facts, ground every line in
  repository evidence or a maintainer answer, and tell the user to evaluate the file on real
  tasks before trusting it.

## 7. Maintenance signals

- Tooling, commands or paths changed: update the file. A stale warning is worse than none.
- Agents keep hunting for the same subsystem, pick the wrong validation, or reviewers repeat the
  same correction: an instruction is missing.
- An instruction no longer changes agent behavior: remove it.

## 8. Scoring rubric (100 points)

Score each dimension from the evidence. If a dimension cannot apply to this repository (for
example no generated code and no layering at all), mark it N/A and renormalize to 100. State the
reason for every N/A.

| # | Dimension | Pts | Full marks when |
|---|---|---|---|
| A | Signal density | 20 | Nearly every line passes the one test. No generic advice, no discoverable facts, no listings, no overview prose, no empty headings |
| B | Commands | 15 | Build, test, lint and run commands are exact, state the working directory where it matters, and explain non-obvious tool choices |
| C | Boundaries | 15 | Generated or restricted paths name the source to edit; dependency direction, compatibility rules and approval-required actions are stated where the repo has them |
| D | Definition of done | 15 | Distinguishes fast checks for iteration from the full check before finishing, and says how validation scales with scope |
| E | Concrete conventions | 10 | Project-specific conventions name canonical files or paths. No "follow existing patterns" |
| F | Accuracy | 15 | Every referenced path exists, every command resolves to a real script or target, nothing contradicts CI or the manifests |
| G | Topology and enforcement | 10 | File placement matches real boundaries, root and nested content are split correctly, no conflicting instructions, duplicated docs replaced by links, rules that tooling can enforce point to the tooling |

Scoring bands inside a dimension: 100% (meets the bar), 70% (minor gaps), 40% (present but vague
or partial), 0% (absent although the repo clearly needs it, or mostly wrong).

### Blockers

Any blocker caps the final grade at C, whatever the points say:

- **B1 Secret**: a credential, token, key or private operational detail in the file.
- **B2 Stale command**: a documented command that does not exist or fails for a structural
  reason (missing script, missing target, wrong directory).
- **B3 Stale path**: an instruction that depends on a path that no longer exists.
- **B4 Contradiction**: two instruction files give conflicting rules for the same code with no
  clear precedence, or the file contradicts what CI enforces.

### Grades

| Grade | Score | Meaning |
|---|---|---|
| A | 85 to 100 | Trustworthy. Maintain it |
| B | 70 to 84 | Useful. Targeted fixes |
| C | 50 to 69 | Mixed signal. Refactor |
| D | 0 to 49 | Likely costs more than it gives. Rewrite from evidence |

## 9. Line dispositions

Every instruction (a bullet, a sentence, a command block) gets exactly one verdict:

| Verdict | When | Action in a refactor |
|---|---|---|
| KEEP | Passes the one test, specific, accurate | Leave untouched |
| SHARPEN | Right intent, vague wording | Rewrite with the exact file, path, command or direction, backed by evidence |
| FIX | Specific but wrong or stale | Correct from repository evidence, or ask |
| MOVE:nested | Applies to one area only | Move to that area's AGENTS.md |
| MOVE:root | Repository-wide rule sitting in a nested file | Move to root |
| MOVE:link | Copy of existing documentation | Replace with a one-line pointer |
| MOVE:tooling | Rule a formatter, linter or CI check could enforce | Point to the tool; propose the tooling change separately |
| CUT | Generic, discoverable, listing, overview, empty heading | Delete |
| REDACT | Secret or private detail | Delete and tell the user to rotate it |

## 10. Size heuristics (not from the source, local rule of thumb)

- Root file above roughly 150 lines: suspect overview prose, duplicated docs or content that
  belongs in nested files. Length alone is never a finding; the content that caused it is.
- Nested file that only repeats the root: delete it.
