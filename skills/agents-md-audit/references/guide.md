# AGENTS.md quality guide and rubric

Shared reference for the `agents-md-audit`, `agents-md-refactor` and `agents-md-create` skills.

Source of the practices: "Writing an effective AGENTS.md", Agentic AI Foundation,
https://aaif.io/blog/writing-an-effective-agents-md. This file restates those practices as
testable criteria. When this file and the source disagree, the source wins; fix this file.

## 1. The one test

For every instruction ask: **would an agent act differently because it read this?**

- If the agent would do the same thing anyway (it can read the manifest, the tree, the code),
  the line is noise. Cut it.
- If the line removes a decision the agent would otherwise guess at, it is signal. Keep it and
  make it exact.

AGENTS.md is plain Markdown. There are no mandatory sections and no schema. A 15-line file can be
excellent. Never reward length, never punish a missing section when the repository has nothing
non-obvious to say there. Files these skills write still use one fixed section order (section 13)
so that they look the same in every repository.

## 2. What belongs in the file

| Category | Good shape | Bad shape |
|---|---|---|
| Layout | Only what names do not reveal: which package owns a feature, which code is shared, where the real entry point is | A tree listing, a tour of every folder |
| Commands | Exact command plus where to run it: "From `services/api`, run `make test-unit`" | "Run the tests" |
| Tooling choices | The non-obvious choice and why: "Use `make build`, not `go build`; the target injects required flags" | Restating the default tool of the language |
| Boundaries | Generated paths and the source to edit instead; dependency direction between layers; public API and compatibility rules; actions that need human approval, kept apart from actions that are never allowed (section 12.2) | "Be careful with the architecture" |
| Definition of done | What to run while iterating, what to run before finishing, how validation scales with the size of the change | "Make sure everything passes" |
| Conventions | Project-specific, concrete, with the canonical file to copy: "New handlers follow `internal/http/orders_handler.go`" | "Follow existing patterns" |

Specificity rule: a vague rule names nothing. Replace it with a file, a path, a command or a
dependency direction, or delete it.

## 3. What does not belong

- Facts visible in manifests or the source tree (language, framework, where tests live, a
  toolchain version the manifest pins; section 12.3).
- Generic engineering advice ("write clean code", "follow best practices", "add tests").
- Directory listings copied from the repository.
- Broad repository overviews. They do not help an agent find the relevant code faster.
- Large copies of existing docs. Link to the doc; two copies drift apart.
- Credentials, secrets, private operational details.
- Template headings with no real content under them.

## 4. Enforcement belongs in tooling

- Style rules go in the formatter config. Layering rules go in static analysis.
- AGENTS.md points at those systems ("lint enforces import order; run `make lint`"). It is not
  the only safeguard.
- Instructions never replace access control or CI checks.

## 5. Topology: root and nested files

- A small repository usually needs one root file.
- A larger repository can add files next to the code they describe (per service, per app).
- Root holds repository-wide rules. Nested files hold area rules: language version, test
  commands, migration rules.
- On conflict, the file closest to the edited file wins. Explicit user instructions beat both.
- Nest only at real boundaries: different language, build system, validation process,
  architecture or ownership.
- Agents differ in how they discover and merge nested files. Test with the agents actually used.

## 6. Evidence caveats (why these skills are conservative)

- Research on context files is mixed. Short, specific files have reduced runtime and tokens.
  Other results show no gain in task success and more steps and cost.
- Files written by developers did better than files generated by an LLM. Generated files only
  helped when other documentation was absent.
- Consequences for these skills: never fill a file with discoverable facts, ground every line in
  repository evidence or a maintainer answer, and tell the user to evaluate the file on real
  tasks before trusting it.

## 7. Maintenance signals

- Tooling, commands or paths changed: update the file. A stale warning is worse than none.
- Agents keep hunting for the same subsystem, pick the wrong validation, or reviewers repeat the
  same correction: an instruction is missing.
- An instruction no longer changes agent behavior: remove it.

## 8. Scoring rubric (100 points)

Score each dimension from the evidence. If a dimension cannot apply to this repository (for
example no generated code and no layering at all), mark it N/A and renormalize to 100. State the
reason for every N/A.

| # | Dimension | Pts | Full marks when |
|---|---|---|---|
| A | Signal density | 20 | Nearly every line passes the one test. No generic advice, no discoverable facts, no listings, no overview prose, no empty headings |
| B | Commands | 15 | Build, test, lint and run commands are exact, state the working directory where it matters, and explain non-obvious tool choices |
| C | Boundaries | 15 | Generated or restricted paths name the source to edit; dependency direction, compatibility rules and approval-required actions are stated where the repo has them |
| D | Definition of done | 15 | Distinguishes fast checks for iteration from the full check before finishing, and says how validation scales with scope |
| E | Concrete conventions | 10 | Project-specific conventions name canonical files or paths. No "follow existing patterns" |
| F | Accuracy | 15 | Every referenced path exists, every command resolves to a real script or target, nothing contradicts CI or the manifests |
| G | Topology and enforcement | 10 | File placement matches real boundaries, root and nested content are split correctly, no conflicting instructions, duplicated docs replaced by links, other agents' instruction files point to AGENTS.md instead of copying it (section 12.1), rules that tooling can enforce point to the tooling |

Scoring bands inside a dimension: 100% (meets the bar), 70% (minor gaps), 40% (present but vague
or partial), 0% (absent although the repo clearly needs it, or mostly wrong).

### Blockers

Any blocker caps the final grade at C, whatever the points say:

- **B1 Secret**: a credential, token, key or private operational detail in the file.
- **B2 Stale command**: a documented command that does not exist or fails for a structural
  reason (missing script, missing target, wrong directory).
- **B3 Stale path**: an instruction that depends on a path that no longer exists.
- **B4 Contradiction**: two instruction files give conflicting rules for the same code with no
  clear precedence, or the file contradicts what CI enforces.

### Grades

| Grade | Score | Meaning |
|---|---|---|
| A | 85 to 100 | Trustworthy. Maintain it |
| B | 70 to 84 | Useful. Targeted fixes |
| C | 50 to 69 | Mixed signal. Refactor |
| D | 0 to 49 | Likely costs more than it gives. Rewrite from evidence |

## 9. Line dispositions

Every instruction (a bullet, a sentence, a command block) gets exactly one verdict:

| Verdict | When | Action in a refactor |
|---|---|---|
| KEEP | Passes the one test, specific, accurate | Leave untouched |
| SHARPEN | Right intent, vague wording | Rewrite with the exact file, path, command or direction, backed by evidence |
| FIX | Specific but wrong or stale | Correct from repository evidence, or ask |
| MOVE:nested | Applies to one area only | Move to that area's AGENTS.md |
| MOVE:root | Repository-wide rule sitting in a nested file | Move to root |
| MOVE:link | Copy of existing documentation | Replace with a one-line pointer |
| MOVE:tooling | Rule a formatter, linter or CI check could enforce | Point to the tool; propose the tooling change separately |
| CUT | Generic, discoverable, listing, overview, empty heading | Delete |
| REDACT | Secret or private detail | Delete and tell the user to rotate it |

## 10. Size heuristics (not from the source, local rule of thumb)

- Root file above roughly 150 lines: suspect overview prose, duplicated docs or content that
  belongs in nested files. Length alone is never a finding; the content that caused it is.
- Nested file that only repeats the root: delete it.

## 11. Finding categories

Every finding has one category. It is the first part of the finding's `key`.

| Category | Dimension | Use for |
|---|---|---|
| `secret` | A (blocker B1) | Credential, token, key or private operational detail |
| `stale_command` | F (blocker B2) | Command that does not resolve in the stated directory |
| `stale_path` | F (blocker B3) | Instruction that depends on a path that does not exist |
| `contradiction` | F or G (blocker B4 when two instruction files or CI conflict) | The file disagrees with another instruction file, CI or a manifest |
| `generic_advice` | A | Advice that applies to any repository |
| `discoverable_fact` | A | Fact an agent reads in seconds from a manifest or the tree |
| `directory_listing` | A | Tree or folder list copied from the repository |
| `overview_prose` | A | Description of the project instead of instructions |
| `empty_heading` | A | Heading with nothing under it |
| `vague_rule` | A or E | Rule that names no file, path, command or direction |
| `missing_cwd` | B | Command without its working directory in a multi-project repo |
| `undocumented_tooling` | B | Wrapper target or non-obvious tool choice the file omits or contradicts |
| `missing_boundary` | C | Generated, vendored or restricted path, or layer rule, with no instruction |
| `missing_validation` | D | CI gate or pre-finish check the file never mentions |
| `duplicated_doc` | G | Copy of README, CONTRIBUTING or another doc inside AGENTS.md |
| `misplaced_scope` | G | Area rule at the root, or repository rule in a nested file |
| `tooling_enforceable` | G | Rule a formatter, linter or CI check could enforce |
| `instruction_drift` | G | Another agent's instruction file copies AGENTS.md or diverges from it instead of pointing to it (section 12.1) |
| `other` | any | None of the above; say why in the summary |

## 12. Criteria from other sources (local rules, not from the source above)

These come from two further posts, restated as criteria: "One AGENTS.md to rule them all",
https://plgah.medium.com/one-agents-md-to-rule-them-all-70e6dc87a05f, and "How to write a great
agents.md: lessons from over 2,500 repositories", GitHub Blog,
https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/.
Neither publishes a method or measurements. They extend sections 1 to 9; where they seem to
disagree with the AAIF source, the source wins.

### 12.1 Other agents' instruction files

- AGENTS.md is the single source. CLAUDE.md, GEMINI.md, `.github/copilot-instructions.md`,
  `.github/agents/*.md`, Cursor rules and similar files reach it by import, link or symlink, and
  add only what concerns that one tool.
- The bridge, per file:
  - CLAUDE.md and GEMINI.md: a line `@AGENTS.md` (`@../AGENTS.md` and so on from a subfolder),
    then the tool's own additions.
  - `.github/copilot-instructions.md`, `.github/agents/*.md`: a one-line pointer to AGENTS.md.
    A custom agent keeps its persona and tool settings and drops the copied commands and rules.
  - Symlink: works, but a checkout without symlink support (the default on Windows) writes a
    one-line text file holding the target path, and the agent reads only that line. Prefer the
    import or the pointer when anyone on the team uses Windows.
  - Tools change how they discover these files. Ask the user to confirm with the agents they use.
- Content that only one tool understands (its slash commands, settings, MCP servers configured
  for it) belongs in that tool's file, not in AGENTS.md.
- A file that copies AGENTS.md lines, or holds rules for the same code without pointing to
  AGENTS.md, is one `instruction_drift` finding on that file, keyed
  `instruction_drift:<file>:agents-md` so that later audits match it. Its fix is in that file:
  reduce it to the bridge plus tool-specific additions. The skills propose that change and make it only on
  request.
- A rule in that file that conflicts with AGENTS.md for the same code is also blocker B4.
- Blockers B2 and B3 are judged on AGENTS.md files. A stale command or path in another tool's
  file is part of its `instruction_drift` finding. A secret is B1 in any file.

### 12.2 Boundaries: ask first versus never

- Keep actions the agent may take after asking apart from actions it must never take. The
  agent behaves differently (stop and ask, or refuse), so a file that mixes them loses
  information.
- Often missing, and only a maintainer can state them: deleting, skipping or weakening a failing
  test to make the suite pass; editing CI configuration; touching deploy or production
  configuration; git actions (commit, push, open a pull request, force-push, rewrite history,
  bypass hooks with `--no-verify`). Ask; never invent these rules.
- A commit format enforced by commitlint or a hook is MOVE:tooling. One documented in
  CONTRIBUTING is MOVE:link.
- Do not ask for an "always do" list. It tends to fill up with generic advice.

### 12.3 Toolchain versions

- A version that a manifest pins (`go` line in `go.mod`, `engines` in `package.json`, `.nvmrc`,
  `.python-version`, `rust-toolchain.toml`, a Gradle toolchain) is discoverable: CUT.
- Write a version only when nothing in the repository pins it, or when the version to use
  differs from the one the tools would pick.
- A version in AGENTS.md that contradicts the manifest is a `contradiction` finding in
  dimension F.

### 12.4 Code examples and order

- A pointer to the canonical file (section 2) beats an inline snippet, which drifts from the code.
  A short snippet is fine when no file shows the pattern on its own and no linter enforces it.
- Put commands near the top; agents come back to them most. Order alone is never a finding.
  Files these skills write follow the fixed order of section 13, which puts commands second.

## 13. Sections, order and language (local rule, for files these skills write)

Every AGENTS.md that `agents-md-create`, `agents-md-refactor` or `agents-md-remediate` writes,
root or nested, uses only these level-2 headings, spelled exactly like this, in this order. So a
file has the same shape in every repository.

| # | Heading | Holds (guide section 2 category) |
|---|---|---|
| 1 | `## Layout` | Layout: ownership, shared code, the real entry point |
| 2 | `## Commands` | Commands and tooling choices: install, build, test, lint, run, with working directory |
| 3 | `## Rules` | Conventions with their canonical file, dependency direction between layers |
| 4 | `## Generated and restricted files` | Boundaries: generated paths and the source to edit, paths not to edit, compatibility rules, actions that need approval |
| 5 | `## Done means` | Definition of done: iteration checks, the full check, how it scales |
| 6 | `## More` | Pointers to other docs, one line each |

- The first line is `# AGENTS.md` in the root and `# AGENTS.md (<dir>)` in a nested file.
- Leave out a section with nothing to say; never add an empty one to complete the set. The
  sections that remain keep this relative order.
- No other level-2 headings. An instruction that seems to fit nowhere goes in the section of its
  category in guide section 2; a group the author wants to keep becomes a `###` heading inside
  that section.
- Headings are always the English ones above, whatever the language of the content, so the
  scanner can check them (`section_order` in its output).
- The content under the headings is written in the language the user asks for. If they name
  none: in a refactor or remediation, the language the existing file is written in; in a new
  file, the language the user writes to you in. Commands, paths and code stay as they are.
- Order is not a quality criterion: the audit does not score it and does not report it as a
  finding.
